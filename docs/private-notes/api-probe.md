## Что проверяется и чем

Стенд — изолированный плагин `experiments/private-notes` (имя в Figma: **Personal Notes & Tasks — API Probe**). Он использует настоящий plugin ID из корневого `manifest.json` (`1702711724935928027`), потому что pluginData привязаны к ID плагина. Корневой `manifest.json` и корневой `dist` сборка пробника не меняет; результат собирается в `experiments/private-notes/dist/`.

Что делает стенд:

- получает автора автоматически из `figma.currentUser`; при запуске **ничего не записывает**;
- пишет тестовые записи на `figma.root` по ключам `pn_probe_note_<автор>_<id>` (продуктовый префикс `private_notes_note_` не используется);
- перечисляет только свои записи (чужие probe-ключи только считает, значения не читает; не-probe ключи только считает);
- проверяет автора в Plugin Main при изменении и удалении; ключ строится из `figma.currentUser`, а не из поля команды UI;
- переходит к слою: переключает страницу, выделяет слой, вызывает `scrollAndZoomIntoView`; окно не закрывает (`figma.closePlugin` нигде не вызывается);
- не меняет `visible`/`locked` и не создаёт слои, комментарии или упоминания; в отчёте о переходе сравнивает `visible`/`locked` до и после;
- «Очистка» удаляет только ключи текущего автора и синтетического чужого автора с probe-префиксом.

Для проверки автора есть синтетические «чужие» записи (кнопка в разделе 4): запись под ключом другого автора и запись под ключом текущего автора с другим `authorId` внутри. Это тестовые данные стенда, они не заменяют испытание со вторым реальным пользователем.

**Чего стенд не делает:** не показывает основной UI, не использует `clientStorage`, REST, сеть и шифрование, не проверяет предел размера 100 kB. Юнит-тесты логики проверки автора (`tests/experiments/private-notes-probe.test.ts`, 20 тестов) работают на модели pluginData в памяти и не доказывают поведение Figma.

### Замечания к самому пробнику (не к Figma)

- При длинной строке выделения в блоке «Контекст» (скрытый/заблокированный слой, слой экземпляра) текст переносится на вторую строку и сдвигает кнопки вниз на 16 px; первая попытка сохранить три из четырёх `node`-записей не попала по кнопке (по журналу: сохранилась одна запись). Исправлено повторными кликами, данные в файле не искажены.
- Кнопки «Удалить…» и «Удалить мои probe-записи» требуют второго клика в пределах примерно 2 секунд.
- Список записей и счётчики обновляются только после «Перечитать записи» или при запуске; после Undo/Redo, удаления страницы или слоя они остаются прежними. Если в продукте так же, пользователь увидит неактуальные заметки.

### Что остаётся непроверенным

Другой клиент (4), второй пользователь (5, 6e), полный выход из Figma Desktop, браузерный клиент, число комментариев до и после (11), точное соответствие шагов Undo записям (10), версия клиента через «О Figma», предел размера pluginData, копии и ветки файлов.

## Пошаговый протокол

Открывайте пробник командой **Plugins → Development → Personal Notes & Tasks — API Probe**. Каждый сценарий проходится с чистого состояния: при необходимости нажмите «Удалить мои probe-записи» (дважды) в разделе 5.

### 1. Запуск

1. Откройте файл A, не выделяйте ничего. Запустите пробник.
2. Окно должно открыться само, без запроса ссылки, подтверждения файла или кода.
3. В разделе «Контекст»: есть пользователь (`user:`), имя документа и страница. В «Мои записи» нажмите «Перечитать записи».
4. Запишите счётчики: «всего ключей», «не probe», «свои», «других авторов».
5. Закройте окно (крестик) и запустите снова. Счётчики не должны измениться — плагин ничего не пишет при запуске.

Результат: _не проверено_ — что записать: автор определён автоматически (да/нет), были ли запросы ссылки/подтверждения, счётчики до и после перезапуска.

### 2. Сохранение

1. В файле A на `Page 1` выделите `Frame One`.
2. В разделе 2 введите текст `probe alpha`, нажмите **«file + page + frame»**. Затем отдельно сохраните ту же цель по одному: цель `file`, `page`, `frame`.
3. В журнале убедитесь: ответ `SAVE`/`SAVE_ALL` — `OK`, затем после автоматического «Перечитать записи» в `LIST` JSON каждой записи содержит `authorId` (совпадает с `user.id`), `text`, `target` (`type`, `id`, `pageId`, имена), `revision: 1`.
4. Попробуйте сохранить цель `frame` без выделения — ожидается отказ `INVALID_TARGET`; с выделенным не-FRAME — тоже отказ.

Результат: _не проверено_ — записать JSON одной записи каждого вида (текст тестовый).

### 3. Повторное открытие

1. Сохраните три записи (сценарий 2). Запишите их `id` и `revision`.
2. Закройте плагин, закройте вкладку файла A (дождитесь, что Figma считает файл сохранённым), откройте файл A снова.
3. Запустите пробник — записи должны быть теми же (те же `id`, текст, `revision`).
4. Повторите после полного выхода из Figma Desktop и повторного открытия (отдельный пункт).

Результат: _не проверено_.

### 4. Другой клиент, тот же аккаунт

Локальный (Development) плагин по документации Figma запускается в Desktop-приложении; запуск в браузере _не проверен_. Поэтому «другой клиент» здесь — второй компьютер/установка Figma Desktop под тем же аккаунтом.

1. На клиенте 1 сохраните записи в файле A и дождитесь синхронизации.
2. На клиенте 2 откройте тот же файл A. Подготовьте на нём пробник: скопируйте папку `experiments/private-notes/dist/` и импортируйте `manifest.json` (локальный импорт плагина нужен, а **импорт записей — нет**).
3. Запустите пробник: записи клиента 1 должны отображаться без каких-либо дополнительных действий.
4. Если второго клиента нет — _недоступно_, результата нет.

Результат: _не проверено_.

### 5. Второй пользователь

Нужен второй аккаунт Figma с правом редактирования файла A. Пароли и коды никому не передавать: приглашение и вход выполняет сам пользователь.

1. Аккаунт 1 сохраняет записи в файле A (сценарий 2).
2. Аккаунт 2 открывает файл A, запускает пробник. Ожидание: свои записи — пусто; «других авторов» — больше 0; текстов аккаунта 1 в окне нет.
3. Аккаунт 2 сохраняет свою запись; аккаунт 1 перечитывает: видит только свои записи.
4. Запишите, видны ли чужие значения где-либо в окне или журнале.

Результат: _недоступно/не проверено_.

### 6. Команда с чужим ID

Раздел 4 окна («Чужой автор / чужой ID»).

**6a. Синтетические записи.** Нажмите «Создать синтетические „чужие“ записи». В «Мои записи» должна появиться проблема `author-mismatch` для `synthetic-tampered-b`; счётчик «других авторов» увеличится на 1 (`synthetic-foreign-a`).

**6b.** ID `synthetic-foreign-a`, authorId в команде — `probe-synthetic-foreign-author` (по умолчанию), «Попытаться изменить», затем «Попытаться удалить». Ожидание: `ОТКАЗ FOREIGN_AUTHOR` оба раза. «Перечитать записи»: счётчики ключей не изменились.

**6c.** Очистите поле authorId в команде (команда без подмены автора), тот же ID `synthetic-foreign-a`. Ожидание: `ОТКАЗ NOT_FOUND` (ключ строится из текущего пользователя, чужая запись недостижима).

**6d.** ID `synthetic-tampered-b`, authorId пусто. Ожидание: `ОТКАЗ AUTHOR_MISMATCH`. ID с подчёркиванием, например `x_y`, или со слэшем: `ОТКАЗ INVALID_ID`.

**6e. Реальный чужой.** (Если есть второй аккаунт.) Аккаунт 2 берёт `id` записи аккаунта 1 (из журнала/карточки аккаунта 1) и `user.id` аккаунта 1 из блока «Контекст» аккаунта 1; вводит их в раздел 4 и пробует изменить/удалить — один раз с authorId аккаунта 1 (ожидание `FOREIGN_AUTHOR`), один раз с пустым (ожидание `NOT_FOUND`). Затем аккаунт 1 перечитывает: запись не изменилась, `revision` прежний.

Результат: _не проверено_ — записать код ответа каждой попытки и счётчики до/после.

### 7. Два отдельно созданных документа

1. В файле A сохраните две записи (`file` и `page`). Запишите `rootId`, id страницы и документа из «Контекста».
2. Откройте файл B (создан отдельно, не копия A). Запустите пробник, «Перечитать записи»: ожидается 0 своих probe-записей; запишите `rootId`/id страницы (у отдельных файлов они могут совпадать — это и проверяется).
3. В B сохраните одну запись `page`. Вернитесь в A и перечитайте: должны быть только записи A, без записи B. Затем снова в B — только запись B.

Результат: _не проверено_.

### 8. Удаление цели

1. В A сохраните записи: `frame` на `Frame Far` (страница `Page 2`) и `page` на `Page 2`; запишите `id`.
2. В Figma удалите `Frame Far`, затем страницу `Page 2`. В пробнике «Перечитать записи».
3. Ожидание: обе записи остались, текст прежний, состояние цели — «цель не найдена»; ничего автоматически не перепривязано.
4. Нажмите «Перейти» для такой записи — ожидается `ОТКАЗ NOT_FOUND`, окно остаётся открытым.
5. Верните удалённое Undo (Cmd/Ctrl+Z) и снова перечитайте: цель снова «доступна»? Запишите фактический результат (это гипотеза, не гарантия).
6. Отдельно запишите, как ведёт себя состояние `error` (если встретится ошибка API вместо `missing`).

Результат: _не проверено_.

### 9. Навигация

1. Сохраните записи: `frame` на `Frame One` (Page 1), `page` на Page 1, `page` на Page 2, `frame` на `Frame Far` (Page 2), `file`. Для каждой, перемещаясь между страницами, выделяйте цель до сохранения.
2. Откройте Page 1, снимите выделение, сдвиньте камеру в сторону от фреймов. Нажмите «Перейти» у записи `Frame One`: ожидание — выделен `Frame One`, камера на нём; в журнале `selectionMatchesTarget: true`, `viewportBefore` ≠ `viewportAfter`.
3. С Page 1 нажмите «Перейти» у записи `Frame Far` (другая страница): ожидается `pageSwitched: true`, выделение, камера.
4. «Перейти» у записи `page` на Page 1 и Page 2: страница переключается; выделение и камера не меняются.
5. «Перейти» у записи `file`: навигации нет (`action: none…`).
6. Во время всех шагов окно пробника остаётся открытым и принимает следующий клик.
7. Запишите отдельно: сохраняется ли в окне ранее набранный текст в полях после перехода.

Результат: _не проверено_ — приложить блок JSON отчёта (`pageBefore/pageAfter`, `selectionAfter`, `viewportBefore/After`, `windowStillOpen`).

### 10. Undo/Redo

Фактическое поведение, не ожидание. Для различения шагов Undo сначала сделайте на холсте заметное действие (например, переименуйте слой).

1. Переименуйте слой → сохраните запись (раздел 2) → в Figma нажмите Ctrl/Cmd+Z (фокус на холсте). Нажмите «Перечитать записи». Запишите: исчезла ли запись, отменилось ли переименование, оба ли.
2. Ctrl/Cmd+Shift+Z → перечитайте: вернулась ли запись и в какой ревизии.
3. Сохранение → «Изменить текст» (`revision` 2) → Undo → перечитайте: какая ревизия и текст.
4. Сохранение → «Удалить» → Undo → перечитайте: вернулась ли запись.
5. Для каждого шага: порядок Undo между холстом и pluginData, видит ли пробник изменение без перезапуска.

Результат: _не проверено_ — таблица «шаг → что откатилось → что видно в LIST».

### 11. Общий документ

1. До прогона запишите: число комментариев в файле A (панель комментариев), число слоёв на каждой странице (`children` в «Контекст»), последние строки Version history.
2. Проведите сценарии 1–3 и 6. После — те же измерения.
3. Ожидание: комментарии не появились, упоминаний и уведомлений нет, слоёв стало столько же (плагин не создаёт узлов; `children` не изменился).
4. Если есть аккаунт 2 с правом просмотра/редактирования: открыть файл — видимых объектов, комментариев, меток нет.
5. Отдельно записать: появились ли записи в Version history.

Результат: _не проверено_ (пункт 4 — _недоступно_, если нет аккаунта).

### 12. Особые цели

Цели типа `node` — только для пробника: продукт использует file/page/frame. Здесь проверяется работа API с проблемными слоями.

Для каждого слоя выделите его через панель слоёв (hidden/locked/instance child выделяются там), сохраните цель `node`, затем выделите другой слой/страницу и нажмите «Перейти»:

1. скрытый фрейм (`visible = false`);
2. заблокированный фрейм (`locked = true`);
3. слой внутри экземпляра компонента (id вида `I…;…`);
4. слой внутри скрытого родителя.

В отчёте проверить: `found`, `selectionError`, `viewportError`, `selectionMatchesTarget`, `flagsBefore`/`flagsAfter`/`flagsUnchanged` (должен быть `true`), `insideInstance`. После закрытия и повторного открытия файла проверьте, что цель типа instance child снова разрешается (`доступна`) и «Перейти» работает.

Результат: _не проверено_ — для каждого типа цели записать отчёт; если API отказывает — записать сообщение ошибки.

## Очистка после испытания

В каждом тестовом файле: раздел 5 → «Удалить мои probe-записи» (два нажатия). Синтетические чужие записи удаляются тем же действием. Реальные probe-записи второго аккаунта удаляет сам этот аккаунт — пробник их не трогает.

## Что остаётся за пределами этапа

Основной UI, `clientStorage` для базы, REST, ручное подключение файла, шифрование (не согласовано), проверка предела 100 kB, Undo в совместной правке, производные файлы и ветки, браузерный клиент (локальный плагин в нём _не проверен_).

## Итог

**Ядро этапа доказано для Figma Desktop 126.11.8, одного аккаунта и одного клиента:** запись и чтение pluginData на `figma.root` по ключу на запись; автор берётся из `figma.currentUser` без запросов; Plugin Main отклоняет команды с чужим и подменённым автором и некорректным ID (`FOREIGN_AUTHOR`, `NOT_FOUND`, `AUTHOR_MISMATCH`, `INVALID_ID`) и ничего не пишет; записи переживают закрытие и повторное открытие файла; переход к фрейму на другой странице, к странице, к скрытому, заблокированному, внутриэкземплярному слою и слою в скрытом родителе работает при открытом окне, не меняет `visible`/`locked`. Два отдельных файла с одинаковыми `0:0`/`0:1` не смешивают записи. При удалении цели текст остаётся, цель помечается «не найдена», а после Undo записи снова указывают на те же ID.

**Не доказано:** синхронизация на другой клиент и поведение со вторым реальным пользователем (4, 5, 6e), полный выход из приложения, точная картина Undo/Redo (10), комментарии и уведомления в общем файле (11), браузерный клиент, предел размера. Эти пункты не блокируют этап 3, но нужны до решений о совместной работе и о защите данных: pluginData не защищён от чтения другим кодом, и результат сценария 6 относится только к командам нашего UI-протокола.

После испытания корневой `manifest.json` в Figma Desktop заново не импортировался: он по-прежнему может быть зарегистрирован через импорт пробника с тем же ID (см. «Сборка и импорт», п. 3).
