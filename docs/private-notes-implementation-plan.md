# Private Notes — план реализации по рабочим сессиям

Дата: 12 ноября 2026 года. Версия: 4. **Статус: хранение, UI и алгоритм согласованы; реализация не начата.**

Папка: `D:\Projects\PrivateNotes`. Основание: [private-notes-architecture.md](private-notes-architecture.md), версия 4.

Основная база — pluginData самого открытого Figma-документа. Запись содержит автора и явную привязку file/page/frame. Plugin Main определяет текущего пользователя и проверяет автора перед чтением/изменением. Прежняя схема clientStorage, fileKey, служебного documentId, ручных ссылок и обязательного локального backup заменена этой версией.

## Правило сессий

**Один этап — одна отдельная рабочая сессия.** Следующий этап автоматически не начинается. Эта сессия меняет только документы, без кода продукта и установки зависимостей.

Перед этапом читать актуальную архитектуру, описание этапа, checkpoint и проверять изменения пользователя. После этапа записывать в будущий docs/private-notes/progress.md результат, изменённые файлы, команды проверок, отдельно реальные испытания Figma, ограничения и следующую задачу.

При изменениях кода/конфигов выполнять pnpm check после восстановления окружения. Моки не заменяют испытание установленного плагина. Непроверенный обязательный результат не объявлять готовым. Незавершённый этап продолжается в следующей сессии с checkpoint.

## Этап 1. Восстановить окружение и обозначить новый продукт

**Цель:** рабочая сборка без реализации заметок.

### Работы

- Восстановить доступ к pnpm и существующую установку по lockfile. Сейчас стандартные пути основных пакетов недоступны; локальный tsc завершился MODULE_NOT_FOUND.
- Не копировать node_modules из другого проекта и не исправлять сгенерированные launcher-файлы вручную.
- Сохранить TS7 через @typescript/native как компилятор; TS6 alias — только для JS API линтера.
- Обновить имя/пути в package.json, manifest.json, index.html, README.md, AGENTS.md для Private Notes.
- Получить отдельный настоящий постоянный plugin ID через Figma. Не придумывать его.
- Manifest: Figma Design, dynamic-page, currentuser, сеть запрещена; private API, OAuth и backend не добавлять.
- Старые материалы Common Structurizer сохранить отдельно, не выдавая их за готовность Private Notes.

**Файлы:** package.json, lockfile при необходимом изменении метаданных, manifest.json, index.html, README.md, AGENTS.md; конфиги только при выявленной несовместимости.

**Проверки:** версии node/pnpm/tsc/eslint; pnpm check; dist/code.js и dist/index.html; импорт manifest в Figma Desktop. Пустые entry point пока не обязаны открывать UI. Старые 15 тестов ссылок не считаются проверкой заметок.

**Не входит:** база, основной UI, новые runtime-зависимости и обновление библиотек.

## Этап 3. Реализовать модель и репозиторий документа

**Цель:** проверенные операции хранения независимо от React.

### Работы

- Модель Note со schemaVersion 1 и discriminated union target file/page/frame по архитектуре v4. Для file не требовать nodeId; для page/frame валидировать соответствующий тип/ID.
- Одна запись — один ключ `private_notes_note_<encodedAuthorId>_<noteId>` на корне.
- Список через getPluginDataKeys с точным префиксом автора; без обхода дерева слоёв.
- Проверять authorId значения; на мутациях брать автора из figma.currentUser, не из UI.
- Создание, редактирование, статус, перепривязка и удаление пустой строкой.
- Не создавать общий перезаписываемый индекс/массив всех авторов.
- Проверять expectedRevision, идемпотентность, поля, Unicode и размер. При перепривязке сохранять ID/автора/createdAt, текст и статус; не создавать дубликат.
- Пределы продукта: 4 000 Unicode-символов, 500 записей автора; предел значения 80 kB с запасом под API entry limit 100 kB.
- Повреждённая запись не очищает остальные; будущая schemaVersion не перезаписывается.
- Подключить shared к обеим проверкам типов без смешивания окружений.

**Файлы:** shared/model.ts, validation.ts; plugin/current-user.ts, storage/document-notes.ts, notes-service.ts; тесты; tsconfig include при необходимости.

**Проверки:** чужой ID, несовпадающий автор, ошибка записи, размер, повтор команды, revision, повреждённая/будущая схема; независимые ключи; pnpm check.

**Не входит:** React, ORM, экспорт, шифрование и миграция ещё не существующей v2.

## Этап 5. Добавление, редактирование и перенос записи

**Цель:** полный жизненный цикл записи с dropdown привязки.

### Работы

- Кнопка «Добавить заметку» открывает plain-text редактор; обычный клик по холсту только меняет контекст.
- Над текстом dropdown «Привязка»: выбранный фрейм, текущая страница, «Весь файл», «Выбрать другую страницу или фрейм…».
- Default — один выбранный FRAME; при пустом выделении — текущая страница. Технический fallback иных/множественных выделений — явно подписанная страница без пакетного создания и угадывания фрейма.
- Поиск/выбор другой цели: страницы и фреймы нужной страницы загружать по требованию; одинаковые названия различать контекстом и ID.
- draftTarget фиксируется при открытии и меняется только dropdown. Клики по холсту и смена страницы не переносят черновик.
- При создании проверить явно выбранную цель и её существование. Не требовать, чтобы она всё ещё была выделена.
- «Весь файл» не требует выделения и отдельного «Отвязать».
- При редактировании оставить id/authorId/createdAt. Текст и новую привязку можно сохранить одним изменением той же записи, без дубликатов и двойной revision.
- Изменение только текста доступно и при потерянной прежней цели; новая привязка проверяется обязательно.
- Автор из Plugin Main, expectedRevision, обновление updatedAt/revision; успех — «Записано в документ».
- Checkbox задачи сохраняет open/done, затем обновляет счётчики/фильтры, не удаляя задачу.
- Удаление с подтверждением: проверить автора/revision, удалить точный ключ, затем убрать карточку и пустую группу.
- Ошибка сохраняет редактор/подтверждённое состояние. Двойной клик и повтор команды не дублируют запись.
- При смене редактируемой записи предложить сохранить/отменить несохранённый текст.

**Файлы:** NoteEditor, TargetDropdown, TargetPicker, подтверждение удаления; plugin/figma/targets.ts, messages.ts, notes-service.ts, state.ts и тесты.

**Проверки:** создать записи file/page/frame; default; file при пустом выделении; выбрать другую страницу/фрейм; сменить выделение во время ввода и сохранить прежнюю выбранную цель; исчезнувшая новая цель; изменение текста при старой потерянной цели; перенос frame → page → file без изменения ID; статус/удаление и счётчики; reject API, конфликт автора/revision, Unicode и повтор команды. Повторное открытие настоящего плагина; pnpm check.

**Не входит:** физический перенос данных между узлами, отдельный слой как четвёртый тип, форматирование, вложения, сроки, autosave каждого символа и несогласованное шифрование.

## Этап 6. Разрешение целей, навигация и актуальная группировка

**Цель:** список и переходы корректно работают с файлом, страницей и фреймом на меняющемся макете.

### Работы

- Для file оставить текущий документ и показать назначение записи без произвольного перехода.
- Для page найти PAGE и переключить страницу; для frame найти FRAME, его актуальный PAGE, переключиться, выделить и показать камерой.
- Окно плагина остаётся открытым.
- Разрешать только нужные цели ограниченными порциями, не сканировать весь документ.
- Подставлять актуальные названия; ключи групп — тип/ID. Переименование не меняет привязку.
- Перемещённый фрейм отображать в его актуальной странице, не доверяя старому pageId.
- Различать unchecked/checking/available/missing/error. Ошибку API не объявлять удалённой целью.
- Для ненайденной страницы/фрейма оставить запись в «Без доступной привязки» с текстом, редактированием, удалением и dropdown перепривязки.
- Не переводить такую запись в file автоматически, не угадывать объект по имени, не менять видимость/блокировку.
- После успешной перепривязки/изменения/удаления обновлять группы, счётчики и пустые разделы.
- Режим текущей страницы охватывает её собственные записи и записи фреймов; режим выбранного фрейма — записи конкретного фрейма.

**Файлы:** plugin/figma/navigation.ts, targets.ts; shared/group-notes.ts, select-notes.ts; NoteGroup/NoteItem, state.ts и bridge.

**Проверки:** три типа перехода; rename и одинаковые названия; перенос фрейма между страницами; удаление/Undo страницы и фрейма; ошибка API против missing; сохранность текста; явная перепривязка; фильтры и счётчики; до 500 своих записей; pnpm check.

**Не входит:** общий обход всех страниц, полный documentchange ради списка и автоматическое изменение смысла потерянной привязки.

## Этап 7. Обновление, Undo и ошибки

**Цель:** согласовать окно с реальными данными документа.

### Работы

- Явное обновление списка и перечитывание при проверяемом возврате фокуса. Пересобирать доступность целей, группы и счётчики, не изменяя draftTarget открытого редактора.
- Перед мутацией перечитывать запись; не восстанавливать отменённое/удалённое из старого UI молча.
- Конфликт revision: сохранить редактор, показать актуальные данные и возможность повторить своё изменение.
- Два окна одного пользователя: разные записи независимы; изменение одной записи не объявлять атомарно защищённым.
- Реально проверить Undo/Redo pluginData и обновление списка.
- Повреждённый JSON одной записи не обнуляет остальные.
- Будущие форматы остаются нетронутыми.
- Отказ API не превращается в успех и не запускает бесконечный повтор.
- Проверить доступную синхронизацию между клиентами Figma.

**Файлы:** document-notes.ts, notes-service.ts, bridge.ts, state.ts, ошибки и тесты.

**Проверки:** Undo сохранения, изменение во втором окне, повреждённая/будущая запись, отказ API; сохранность корректных записей и черновика; ручной протокол Undo/Redo; pnpm check.

**Не входит:** собственная облачная синхронизация, обязательный backup из-за локальной базы, загрузка всех страниц и обещание мгновенной межоконной актуальности.

## Что согласовано, а что остаётся открытым

**Согласованы пользователем в обсуждении:**

- основная база pluginData на корне текущего Figma-документа, проверка автора в Plugin Main;
- три логических уровня привязки file/page/frame;
- dropdown над редактором, defaults по контексту и явное изменение цели;
- цель черновика не следует за кликами по холсту;
- единый сгруппированный список со сворачиванием, поиском, фильтрами и счётчиками;
- создание, редактирование, выполнение, подтверждаемое удаление, перенос без дубликатов;
- сохранение текста при недоступной цели, явная перепривязка;
- обновление из документа и обнаружение конфликта вместо молчаливой перезаписи;
- один этап за отдельную рабочую сессию.

**Не выдавать за согласованные требования:**

- конкретный механизм шифрования и источник/восстановление ключа. Web Crypto исследован как кандидат, но не выбран окончательным решением и не реализован;
- пароль, обязательный экран разблокировки, локальное хранение ключа или backend для ключей;
- точные визуальные размеры окна, числовые продуктовые пределы и технический fallback нетипичного выделения: это настройки реализации, не отдельные пользовательские решения;
- мгновенная синхронизация уже открытых окон и автоматическая обработка производных/ветвящихся документов.
