# Private Notes — архитектура

Дата: 12 ноября 2026 года. Версия: 4. **Статус: хранение, UI и алгоритм согласованы в обсуждении; реализация не начата.**

Рабочая папка: `D:\Projects\PrivateNotes`. План: [private-notes-implementation-plan.md](private-notes-implementation-plan.md).

Эта версия заменяет прежнее решение с локальным хранилищем. **Заметки хранятся внутри текущего Figma-файла. Пользователь выбирает привязку «Весь файл / Страница / Фрейм». Плагин автоматически определяет автора и показывает его записи.** Ввод ссылок, fileKey, служебная метка документа и clientStorage для основной базы не нужны.

## 1. Согласованный интерфейс

### Привязка заметки

Пользователь выбирает логическую привязку, а не физическое место хранения. Все записи остаются на корне Figma-документа. В dropdown есть три уровня:

| Значение            | К чему относится заметка |
| ------------------- | ------------------------ |
| Весь файл           | Документ целиком         |
| Страница · название | Конкретная страница      |
| Фрейм · название    | Конкретный фрейм         |

Над полем текста расположен dropdown, например **«Привязка: Фрейм · Checkout ▾»**. Доступные пункты: выбранный фрейм (если есть), текущая страница, «Весь файл» и «Выбрать другую страницу или фрейм…». Последний открывает поиск/выбор цели по названию. Одинаковые названия различаются контекстом страницы и иерархии; идентификатором остаётся ID.

При открытии нового редактора один выбранный FRAME становится целью по умолчанию; при пустом выделении — текущая страница. Выбор «Весь файл» выполняется явно. Обычное выделение обновляет контекст окна; редактор открывается кнопкой «Добавить заметку», а не каждым кликом по холсту.

Автоматического пакетного создания при множественном выделении нет. Для иных выделений технический fallback — явно подписанная текущая страница и возможность выбрать цель в dropdown; не угадывать случайный фрейм и не добавлять четвёртый уровень «отдельный слой» без обсуждения.

После открытия редактора его цель зафиксирована. Пользователь может менять её только dropdown. Новое выделение или смена страницы не перемещают набираемую заметку. При сохранении проверяется существование выбранной в редакторе цели, а не совпадение с текущим выделением.

Отдельная команда «Отвязать» не нужна: «Весь файл» снимает конкретную привязку к странице/фрейму. У существующей записи доступен такой же dropdown.

### Список и группировка

Согласован один список с группировкой, а не три таба «Файл / Страницы / Фреймы»:

- «Весь файл» — записи документа целиком.
- «Страница · Mobile» — сначала собственные записи страницы, затем группы её фреймов.
- «Фрейм · Checkout» — записи конкретного фрейма внутри группы его текущей страницы.
- «Без доступной привязки» — записи, цель которых не найдена.

Группы сворачиваются; пустые группы не показываются. Счётчик страницы включает её прямые записи и записи сгруппированных в ней фреймов. Одна заметка учитывается один раз. Сворачивание не влияет на счётчики.

Над списком — поиск, фильтры «Все / Заметки / Открытые задачи / Выполненные задачи» и переключатель «Все заметки / По текущему выбору». Режим текущего выбора показывает записи одного выбранного фрейма; если одного FRAME нет, используется текущая страница. В режиме страницы показываются её прямые записи и записи её фреймов. Записи «Весь файл» доступны в общем режиме.

Сначала применяются поиск и фильтры, затем строятся группы и их счётчики по видимым записям. Поиск не вызывает запись данных и не ищет по записям других авторов. Переключение списка не изменяет привязку черновика.

Пока доступность цели проверяется, запись не объявляется потерянной. Ошибка API отличается от результата «не найдено»: показывается ошибка и повтор проверки, без изменения самой привязки.

### Что пользователь может делать

Обычная заметка содержит plain text. Задача дополнительно имеет состояние «Открыта» / «Выполнена». Можно создать несколько записей для одной цели, редактировать текст, менять привязку, выполнять/возвращать задачу, удалять запись с подтверждением, переходить к цели и обновлять список.

Нет настройки подключения файла, собственной регистрации, обычных Figma-комментариев, упоминаний и видимых текстовых слоёв. Через механизм комментариев коллегам ничего не отправляется.

Первая версия — авторизованный пользователь Figma Design с правом редактирования. Desktop и браузер проверяются отдельно. Backend, OAuth, REST, AI, сроки и уведомления при закрытом плагине не входят в согласованный MVP.

## 2. Где и как хранить заметки

Используем `figma.root.setPluginData/getPluginData/getPluginDataKeys`. Это метаданные самого текущего документа; API поддерживает их на DocumentNode. [S1, S2]

**Одна заметка — одно значение на корне документа.** Внутри записи лежат автор, текст, статус и тип привязки file/page/frame с соответствующим ID. Пользователь выбирает привязку в dropdown; физическое хранение остаётся на корне, поэтому удаление страницы или фрейма не уничтожает текст заметки.

Ключ записи:

`private_notes_note_<encodedAuthorId>_<noteId>`

Части ключа кодируются однозначно. noteId — случайный уникальный ID, например UUID. Значение — JSON одной записи. Общего массива всех пользователей и отдельно записываемого индекса не требуется.

### Чтение

1. Plugin Main получает `figma.currentUser.id`.
2. Вызывает `figma.root.getPluginDataKeys()`.
3. Оставляет только ключи с точным префиксом текущего автора.
4. Читает и проверяет каждое выбранное значение.
5. Дополнительно проверяет authorId внутри записи.
6. Отправляет в React только записи текущего пользователя.

Нет обхода всех слоёв и загрузки всех страниц для поиска заметок. Контекст документа уже задан объектом figma.root. При одинаковых nodeId в двух отдельно созданных документах чтение происходит из разных корней — смешивать их не нужно.

### Создание, изменение и удаление

- Автор присваивается в Plugin Main из текущего пользователя, а не из полей команды React.
- При изменении повторно проверяются автор, ID записи и ожидаемая revision.
- Один setPluginData сохраняет одну запись, не перезаписывая весь список.
- Удаление — setPluginData с пустой строкой для точного ключа своей записи. [S1]
- Повторное создание с тем же noteId и теми же данными не создаёт дубликат.
- Неизвестный или повреждённый формат не заменяется пустой записью.

Раздельные ключи не заставляют разных пользователей перезаписывать один общий JSON. Одновременное изменение одной записи одним пользователем в двух окнах всё ещё требует обнаружения конфликта; read/check/write не является атомарной блокировкой.

## 3. Проверка автора и шифрование

**Принятая основа пользовательского поведения:** человек видит и меняет только свои записи через наш плагин. Проверка выполняется в Plugin Main на чтении и каждой операции; скрытия карточек средствами React недостаточно.

Проверка authorId и криптографическое шифрование — разные механизмы. Первый определяет поведение нашего приложения; второй может защищать сами сохранённые тексты. Шифрование технически совместимо с pluginData, поэтому хранение внутри файла нельзя объявлять неподходящим только из-за вопроса приватности.

Базовая схема этой версии использует проверку автора. Шифрование не добавляется автоматически по упоминанию как возможного варианта. Если оно войдёт в требования, отдельно определить, как пользователь получает и восстанавливает ключ расшифровки. ID аккаунта не является секретным ключом. Это не основание возвращаться к clientStorage или вводить backend по умолчанию.

Точное обещание базовой версии: **плагин не показывает чужие записи**. Не писать в интерфейсе «данные зашифрованы», если шифрования нет. Figma документирует pluginData как данные плагина, но не как криптографическую защиту содержимого документа. [S1]

## 4. Сохранение и работа в разных клиентах

Заметки становятся частью Figma-документа и сохраняются/синхронизируются вместе с его данными средствами Figma. Это не отдельная локальная база приложения.

- При открытии того же синхронизированного документа тем же аккаунтом в другом клиенте плагин должен прочитать те же записи; этот сценарий проверяется реальным стендом.
- Очистка локального хранилища плагина больше не является причиной удаления нашей основной базы: мы её там не храним.
- Плагин не реализует собственный облачный сервис и не обещает подтверждение серверной синхронизации Figma, которого Plugin API не вернул.
- После успешного setPluginData UI сообщает «Записано в документ». Это не отдельная гарантия, что офлайн-изменение уже дошло до сервера.
- Несохранённый текст редактора хранится в памяти окна и может пропасть при закрытии.
- Для записи нужны права изменения документа; режим только просмотра не входит в MVP.
- Plugin ID должен оставаться постоянным: данные привязаны к ID плагина. [S1]
- Плагин сам не создаёт копии файлов. Производные документы и ветки не являются условием старта текущего MVP.

Влияние Undo и поведение при параллельной работе проверяются до выпуска. Не записывать заметки заново из устаревшего UI, если пользователь уже отменил/изменил их в документе.

## 5. Модель записи

| Поле                    | Назначение                                                                               |
| ----------------------- | ---------------------------------------------------------------------------------------- |
| schemaVersion           | Версия формата; первая — 1                                                               |
| id                      | Уникальный ID записи                                                                     |
| authorId                | ID создавшего пользователя Figma                                                         |
| kind                    | note или task                                                                            |
| text                    | Непустой обычный текст                                                                   |
| status                  | Для note — null; для task — open/done                                                    |
| target.type             | file, page или frame                                                                     |
| target.id               | null для file; ID страницы для page; ID фрейма для frame                                 |
| target.pageId           | null для file; ID самой страницы для page; последняя известная страница фрейма для frame |
| target.nameSnapshot     | Последнее известное название цели                                                        |
| target.pageNameSnapshot | Последнее известное название страницы; null для file                                     |
| createdAt, updatedAt    | UTC-время в миллисекундах Unix                                                           |
| revision                | Версия конкретной записи для обнаружения устаревших изменений                            |

Тип привязки — discriminated union: file не содержит обязательного nodeId, page указывает PAGE, frame указывает FRAME. Несовместимые сочетания отклоняются в runtime. Имя документа/страницы/фрейма не используется как ключ. Для file не требуются fileKey или искусственный documentId: запись уже находится на корне текущего документа.

Актуальная страница фрейма определяется по его родителям, а не по устаревшему target.pageId. Подписи и группировка могут обновляться в памяти без автоматической перезаписи записи; снимки обновляются при явном сохранении/перепривязке.

Состояние редактора содержит отдельную draftTarget. Она инициализируется при открытии формы и далее меняется только dropdown. Состояние текущего выделения хранится отдельно: оно управляет фильтром/предложением новой цели, не перезаписывая draftTarget.

Предлагаемые технические пределы: 4 000 Unicode-символов на запись и 500 записей автора в документе. Это настройки реализации, не отдельные утверждённые пользователем требования и не лимиты количества заметок Figma.

У pluginData есть лимит **100 kB на одну запись ключ/значение с учётом plugin ID**. Поэтому весь блокнот не складывается в один JSON. Проверять сериализованный размер; предлагаемый внутренний предел — 80 kB на значение с запасом. Лимит 5 MB clientStorage к этой архитектуре не относится. [S1]

Состояние разрешения цели — unchecked / checking / available / missing / error — хранится в памяти. Статус задачи от него не зависит. Ненайденная страница/фрейм не удаляет заметку и не превращает её в запись «Весь файл».

## 8. Согласованный алгоритм управления заметками

### 8.1. Открытие

1. Открыть React UI и дождаться READY.
2. Получить текущего пользователя в Plugin Main.
3. Перечислить ключи записей на figma.root, отобрать префикс автора, прочитать и проверить значения и authorId.
4. Передать только собственные корректные записи. Повреждённые свои значения показать как частичную ошибку, не сбрасывая остальные.
5. Получить текущую страницу и снимок выделения.
6. Разрешить нужные цели ограниченными порциями и построить список по разделу 1.

При первом запуске пустая база нормальна. Ввод ссылки и предварительная служебная метка не нужны.

### 8.2. Добавление и dropdown

1. По кнопке «Добавить заметку» создать черновик с новым ID и целью по текущему контексту.
2. В редакторе показать тип и название цели над текстом.
3. Выбор другого значения dropdown изменяет только draftTarget, пока пользователь не сохранит.
4. Для «Выбрать другую страницу или фрейм…» сначала получить список страниц; фреймы загружать по нужной странице по требованию, не обходить весь документ при запуске.
5. Обычные клики по холсту не меняют draftTarget. Цель файла не требует выделения.

### 8.3. Создание записи

1. Проверить непустой текст, формат команды и выбранную draftTarget.
2. Для page найти PAGE по target.id; для frame — FRAME и его актуальную страницу. Для file проверки выделения нет.
3. Если конкретная цель исчезла, оставить редактор и текст; предложить другой выбор привязки, не подставлять его автоматически.
4. Назначить authorId из текущего пользователя, даты и начальную revision.
5. Записать один JSON по ключу новой записи через setPluginData.
6. После успешного API-результата показать «Записано в документ», добавить карточку, пересчитать группы и счётчики.
7. При исключении оставить черновик и показать повтор действия. Повтор с тем же ID не создаёт вторую заметку.

Между выбором цели и сохранением она может перестать быть выделенной — это не ошибка само по себе. Важно, существует ли явно выбранная цель и допустим ли её тип.

### 8.4. Чтение, поиск и группировка

Для file — группа «Весь файл». Для page — прямые записи этой страницы. Для frame — группа этого фрейма внутри его актуальной страницы. Ключи групп строятся из типа и ID, не названия.

Применить фильтры к своим записям, сгруппировать, отсортировать детерминированно и вычислить счётчики. Исходные записи не изменяются поиском, фильтрами и сворачиванием. Актуальные названия брать из найденных объектов; при недоступности использовать сохранённые подписи с объяснением состояния.

После собственной операции обновить затронутую запись и представление. Полную базу при сохранении одной заметки не перезаписывать.

### 8.5. Редактирование и перенос привязки

1. Открыть существующую запись в редакторе, скопировав текст и target в черновик.
2. Перед сохранением перечитать запись и проверить автора/expectedRevision.
3. Изменить текст и/или target, сохранив id, authorId и createdAt.
4. Увеличить revision, обновить updatedAt и записать тот же ключ.
5. После успеха переместить карточку в новую группу, не создавая дубликат.
6. При конфликте/ошибке сохранить черновик для решения пользователя.

Старую недоступную цель можно оставить при редактировании одного текста: проверка существования обязательна для новой/изменённой привязки, но отсутствие прежней цели не блокирует сохранение личного текста. Автоматического перевода в file нет.

### 8.6. Статус задачи

Checkbox создаёт команду для одной task-записи. Plugin проверяет автора/revision и записывает новый status. После успеха меняются карточка, счётчики и попадание в фильтр; выполненная задача не удаляется. При ошибке подтверждённый статус остаётся прежним, показывается причина.

### 8.7. Удаление

1. Получить подтверждение удаления конкретной заметки.
2. В Plugin Main перечитать её, проверить автора и expectedRevision.
3. Удалить только её значение через setPluginData(key, '').
4. После успеха убрать карточку, пересчитать счётчики и скрыть пустую группу.
5. При ошибке не прятать запись как успешно удалённую.

### 8.8. Переход, потерянная цель, обновление

Поведение перехода зависит от типа и описано в разделе 9. Результат «цель не найдена» сохраняет текст и исходную target; в UI запись появляется в «Без доступной привязки» с редактированием/удалением/перепривязкой.

Кнопка «Обновить» перечитывает данные документа и актуальность целей. Собственные успешные операции обновляют список сразу. Перед любой мутацией перечитывается конкретная запись: чужое изменение не затирается молча. Мгновенная межоконная актуальность не обещается.

### 8.9. Сообщения React и Plugin Main

Команды имеют protocolVersion, requestId, runId. runId отсеивает запоздалые ответы, но не идентифицирует документ. Автор и доступ определяются в Plugin Main.

| Команда         | Вход                                                  | Результат                                     |
| --------------- | ----------------------------------------------------- | --------------------------------------------- |
| READY           | Версия протокола                                      | Автор, свои записи, страница и выделение      |
| REFRESH_NOTES   | requestId                                             | Перечитанные собственные записи               |
| LIST_TARGETS    | Тип page/frame, выбранная страница и поисковая строка | Допустимые цели для dropdown с ID и подписями |
| CREATE_NOTE     | id, kind, text, явно выбранная target                 | Сохранённая запись с автором из Plugin Main   |
| UPDATE_NOTE     | id, text, expectedRevision                            | Обновлённая запись без неявной смены цели     |
| SET_TASK_STATUS | id, status, expectedRevision                          | Подтверждённый статус                         |
| DELETE_NOTE     | id, expectedRevision                                  | Подтверждённое удаление                       |
| FOCUS_NOTE      | id                                                    | Результат перехода по типу цели               |
| REBIND_NOTE     | id, явно выбранная target, expectedRevision           | Обновлённая цель той же записи                |
| REFRESH_TARGETS | ID отображаемых записей                               | Доступность/подписи нужных целей              |

Текст и target можно сохранять одной командой UPDATE_NOTE, записывающей один JSON с явно указанным patch, чтобы изменение обоих полей не превращалось в два конфликтующих сохранения. Отдельный REBIND_NOTE нужен для самостоятельного действия переноса. Реальный контракт не должен иметь двух разных правил обновления.

UI-состояния: загрузка, пустой блокнот, список, новый редактор, редактирование, запись в документ, подтверждение удаления, ошибка/конфликт. Текст и ключи шифрования не логируются. В bridge нет объектов Figma и доверия к переданному authorId.

Шифрование в будущем вставляется перед записью, расшифровка — после чтения до поиска/показа. Выбор алгоритма и источника ключа не согласован и не является уже реализованной частью этого алгоритма.

## 9. Навигация, обновление и Undo

| Тип цели | Действие                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------- |
| file     | Оставить открытый документ; показать, что запись относится ко всему файлу, без произвольного перехода                 |
| page     | Найти PAGE и вызвать setCurrentPageAsync; конкретный фрейм не выделять                                                |
| frame    | Найти FRAME, определить его актуальную страницу, переключиться, выделить фрейм и показать через scrollAndZoomIntoView |

Переименование не меняет связь по ID. Для перемещённого фрейма использовать актуального предка PAGE, а не старый target.pageId. При удалении страницы/фрейма запись на корне остаётся; восстановление цели после Undo проверяется повторным разрешением её ID. Не угадывать замену по названию и не снимать блокировку/видимость ради перехода.

Полный documentchange в dynamic-page требует загрузки всех страниц. Не загружать весь документ только ради событий. Записи перечитываются через REFRESH_NOTES по кнопке «Обновить» и при проверяемом возврате фокуса; перед мутацией — конкретная запись.

Undo/Redo могут изменить pluginData. После обновления источник истины — документ. Устаревшая карточка не должна молча восстанавливать удалённую запись. Сохранить пользовательский черновик и объяснить конфликт.

## 10. Проверка автора, ошибки и независимые записи

Два уровня проверки автора обязательны: префикс ключа и authorId значения. Мутации также проверяют текущего пользователя в Plugin Main. Чужой id не должен позволить прочитать/изменить/удалить запись через команды нашего плагина.

При чтении списка повреждённая своя запись не должна обнулить остальные: показать число непрочитанных записей и оставить корректные доступными. Неизвестная будущая schemaVersion не перезаписывается старой версией плагина.

Различать: недоступный пользователь, неверная команда, чужая/отсутствующая запись, неверная схема, конфликт revision, превышение размера, ошибка записи, ненайденный слой и ошибка API. Ошибка поиска цели не означает, что текст надо удалить.

## 12. Готовность и источники

API поддерживает чтение/запись pluginData на корне, чтение автора и навигацию. Сам новый плагин пока не написан. Этап 2 проверяет реальное сохранение, автора, повторное открытие/синхронизацию и переход; это не повод возвращать ручные ссылки или локальную базу.
